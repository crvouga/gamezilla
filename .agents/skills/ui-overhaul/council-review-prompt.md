# Council review prompt: ui-overhaul

`scripts/council-round.mjs prompt` fills the `{{PLACEHOLDERS}}` between the markers and writes
the question file you pass to Agent Council. Do not edit this file during a run: `init` records
its hash, and `verdict` marks every round incomplete once the rubric changes. To change the
rubric, ask the user, then start a new run with a new baseline.

<!-- prompt:start -->

You are one independent member of a design review council. Rate the UI design and the UX of
{{PRODUCT}} at one exact revision. Other members rate the same evidence separately; do not
guess what they will say.

## This review

- Skill: ui-overhaul. Polish the existing UI with minimal disruption. Allowed: typography,
  spacing, alignment, contrast, visual hierarchy, focus visibility, consistency. Not allowed:
  changes to navigation, screen composition, control placement, labels or task steps.
- Round {{ROUND}} ({{KIND}}). Starting revision: {{START_SHA}}. Candidate revision:
  {{CANDIDATE_SHA}}. Evidence set: {{EVIDENCE_ID}}.
- What changed in this round: {{CHANGES}}

## Evidence (paths are relative to your working directory)

- Candidate ("after") evidence: `{{EVIDENCE_DIR}}`. Start with `index.md` there: it lists every
  screenshot with its screen, state, viewport and theme, the Storybook story ID, and the
  interaction log for each journey.
- Starting ("before") evidence: `{{BEFORE_DIR}}`, captured with the same data, viewports and
  themes.
- Primary journeys:
  {{JOURNEYS}}
- Screens and states in scope:
  {{SCREENS}}

OPEN AND LOOK AT EVERY IMAGE LISTED IN BOTH INDEX FILES BEFORE SCORING, and read every
interaction log. Judge only what you see. If an image will not open, say which one and do not
score. Names, avatars and data are fixtures; do not judge them.

## Rubric (fixed for the whole run)

Score each dimension from 0 to 10 (halves allowed): 10 = best-in-class shipped product, 9 =
polished, with only nitpicks left, 8 = solid professional product with minor issues, 6 =
functional but generic or unpolished, 4 = noticeably flawed, 2 = broken.

- Design: visual hierarchy, typography, spacing and alignment, color and contrast (WCAG 2.2 AA
  text and non-text contrast), visible keyboard focus, consistency across screens, responsive
  layout at every viewport shown, polish (no clipping, overlap, misalignment or awkward empty
  space).
- UX: whether a person can tell what to do and complete each journey, steps and effort per task,
  feedback for loading, empty, error and success states, clarity of labels and messages, error
  prevention and recovery, interaction accessibility (focus order, target size, keyboard and
  screen-reader names as the logs show them).

Every deduction must name the screen and state, or the journey step, that caused it. Rate the
candidate against the rubric, not against the starting revision: an improved screen can still
score low.

Score the starting ("before") evidence too: {{SCORE_BEFORE}}. When yes, rate it with the same
rubric and report DESIGN BEFORE and UX BEFORE. When no, leave those two lines out.

Scope check: say SCOPE: violated if the candidate changes navigation, screen composition,
control placement, labels or task steps compared with the starting evidence, and name where.

## Answer format

Use your usual sections, and end with this block exactly, one value per line:

## Ratings

CANDIDATE: <the candidate revision exactly as given above>
EVIDENCE: <the evidence set exactly as given above>
DESIGN AFTER: <n>/10
UX AFTER: <n>/10
DESIGN BEFORE: <n>/10
UX BEFORE: <n>/10
SCOPE: respected | violated - <where>
TOP FIX: <the single most important remaining fix, with its screen or journey step>

## Deductions

One line per deduction: `<design|ux> -<points> <screen/state or journey step>: <problem> -> <fix>`
<!-- prompt:end -->
